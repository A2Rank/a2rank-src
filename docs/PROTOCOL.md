# AION2 클라이언트 수신 패킷 명세 (랭킹 포인트 관련)

2026-10-10~11 실제 전투 수신 데이터(`testdata/battle_2026-10-10.log`)와
게임 화면(채팅 로그)을 대조해 확인한 내용. 서버 → 클라이언트 방향만 다룬다. 패킷을 보내지 않는다.

표기: `u16/u32/u64` = little-endian 부호 없는 정수, `i32` = little-endian 부호 있는 정수,
`varint` = 아래 정의, `str` = `varint 길이` + UTF-8 바이트.

---

## 1. 전송 계층

| 항목 | 값 |
|---|---|
| 프로토콜 | TCP (IPv4/IPv6) |
| 서버 포트 | **13328** (수신 패킷의 출발지 포트) |
| 캡처 필터 | `tcp src port 13328` |
| 연결 | 지역 이동 등에서 연결이 닫히고(FIN/RST) 새 연결이 맺어진다. 동시에 연결이 여러 개일 수 있다 |

TCP 스트림은 순서번호(seq)로 재조립한다. 2초 이상 빈 구간이 이어지면 "끊김(gap)"으로 보고
스트림을 다시 동기화한다. 끊김은 포인트 증감의 근거가 아니다.

## 2. 프레임

스트림은 프레임의 연속이다.

```
[varint L][payload ...]
```

- **varint**: 바이트마다 하위 7비트가 값, 최상위 비트(0x80)가 1이면 다음 바이트가 이어진다.
  최대 5바이트. `value |= (b & 0x7F) << (7*i)`.
- 프레임 전체 크기(길이 필드 포함) = `L - 4 + (varint 바이트 수)`.
  payload = 프레임에서 길이 필드를 뺀 나머지.
- 크기 상한 2 MiB (그 이상은 잘못된 동기화로 본다).

### 2.1 압축 payload

payload가 `FF FF`로 시작하면 압축 묶음이다.

```
FF FF  u32 원본크기  [LZ4 raw block ...]
```

- LZ4 *block* 형식(프레임 헤더 없음). 해제 결과 크기가 `원본크기`와 정확히 같아야 한다.
- 해제한 버퍼 안에는 **같은 형식의 프레임**(varint 길이 + payload)이 여러 개 들어 있다.
  각 내부 payload가 메시지 하나다.

압축이 아니면 payload 자체가 메시지 하나다.

### 2.2 중간부터 받기 시작했을 때(동기화)

캡처를 켠 시점이 프레임 경계가 아닐 수 있다. 버퍼 앞에서 한 바이트씩 밀면서, 그 위치부터
**유효한 프레임이 3개 연속**(또는 내부 메시지 3개 이상을 담은 유효한 압축 묶음 1개) 읽히는
첫 위치를 찾아 거기서부터 읽는다. "유효"는 크기 범위가 맞고 메시지 앞 2바이트가 알려진
종류(아래 opcode 목록의 두 번째 바이트 계열)인 경우.

## 3. 메시지

메시지 앞 2바이트가 종류(opcode)다. 이 프로젝트가 쓰는 것만 정리한다.

| opcode | 이름 | 용도 |
|---|---|---|
| `73 E2` | 랭킹 포인트 | 내 총 랭킹 포인트 |
| `04 8D` | 사망 | 주변에서 일어난 사망 (PvP/PvE) |
| `45 36` | 신원 | 주변 캐릭터의 내부 번호 ↔ 이름/서버/종족 |
| `55 8D` | 랭킹 목록 | 랭킹 화면 목록 + 다음 갱신 시각 |
| `57 8D` | 내 랭킹 | 내 순위 한 줄 + 다음 갱신 시각 |
| `33 36` | 입장 | 접속·캐릭터 변경·지역 이동 때 내 내부 번호·이름·서버 (수 KB) |
| `A9 FF` | (포인트 동반) | 포인트가 바뀔 때마다 같이 오는 18바이트 고정값. 정보 없음 |

### 3.1 `73 E2` 랭킹 포인트

```
73 E2 00  u64 총포인트          (메시지 길이 정확히 11)
```

- 값이 바뀔 때마다 온다. **증감 = 이번 값 − 직전 값**. 게임 채팅의
  "N 랭킹 포인트를 획득/잃었습니다"와 1:1로 일치(검증: 21:31, 21:38, 21:44, 21:53, 22:00~22:04 구간 전부).
- 한 번의 처치에 포인트 메시지가 2번 나뉘어 올 수 있다(예: +24, +25가 0.04초 간격).
- 같은 TCP 묶음 안에 여러 개가 올 수 있다(한타 중 같은 시각에 +540, +67).

### 3.2 `04 8D` 사망

```
04 8D
varint 피해자 내부번호
u32    스킬
varint 처치자 내부번호
u16    처치자 서버코드
str    처치자 이름
str    처치자 길드
u16    처치자 종족 (1/2, 그 밖이면 서버코드로 추정)
...    (미확인)
u8     마지막 바이트: 1 = PvP
```

- **주변의 모든 사망이 온다.** 내가 관여하지 않은 아군·적군 사망도 포함.
- 시야 밖에서 일어난 처치는 오지 않는다(이때 포인트만 들어온다).
- 내부번호는 지역/연결마다 바뀔 수 있다.

### 3.3 `45 36` 신원

```
45 36
varint 내부번호
5바이트 (미확인)
str    이름
u32    레벨 (1~100)
u8     종족 (1 또는 2)
...    서버/길드 구간
```

서버 코드는 고정 위치가 아니다. 이름 뒤 약 200바이트 안에서 다음을 만족하는 위치를 찾는다:
`u16 서버코드`가 유효 범위이고, 같은 값이 8바이트 뒤에 한 번 더 있고, 그 뒤에
`str 길드` + `u16 종족`이 이어지며 종족이 서버코드의 진영과 맞는다. 

이 형식이 아닌 신원(녹화 256건 중 89건, 약 1/3)은 코드가 한 번만 나온다. 이름 뒤 고정 구간 다음에
`u32 100000`이 두 번 연속으로 나오고(표식 `a0 86 01 00 a0 86 01 00`), 그 뒤 플래그·varint 몇 개를 지나 서버 코드가 온다
(`... 01 <varint> <varint> fb 03 ...`, varint 개수는 가변). 표식 뒤 8바이트부터 80바이트 안에서 종족이 맞는
첫 서버 코드를 쓴다. 검증: 기존 방식이 찾은 167건과 100% 일치, 놓쳤던 89건 모두 해결(전 녹화 서버 미확인 0건).
표식을 못 찾으면 서버 미확인(0).

### 3.4 `55 8D` / `57 8D` 랭킹

```
offset 4: u8 순위표 (01 = 랭킹 포인트: 이것만 쓴다. 03 보스, 04 던전, 05·06, 15 = 다른 순위표인데 같은 모양으로 오고, 같은 이름으로 다른 점수·순위가 온다)
offset 5: u8 분류 (0 = ALL, 그 밖 = 직업별)
offset 6부터:
  55 8D (목록):  varint 개수, 항목 × 개수, u64 다음갱신(ms, epoch), u32 전체수
  57 8D (내 것): 항목 1개,             u32 전체수, u64 다음갱신(ms, epoch)
항목:
  u32 순위, u64 식별자(상위 16비트 = 서버 관련 코드, 하위 48비트 = 캐릭터 번호),
  ※ 내 랭킹의 상위 16비트는 게임 내 서버와 다를 수 있다: 아라·보리 모두 입장/사망 메시지는 1019, 랭킹은 1006.
  str 이름, str 길드, u16 종족, u32 레벨, u32 (미확인), u8 직업, u64 점수,
  str 통계(JSON 객체), i32 × 4 (미확인)
```

- **다음갱신 시각**: 게임의 랭킹 초기화 시각. 실측 23:13:54 ↔ 게임 표시 남은 시간 28:20 (입력 지연 13초).
  매시 같은 분·초에 갱신된다.
- 랭킹 화면을 열 때와, 열지 않아도 10~60분 간격으로 `57 8D`가 온다.
- 유효성: 다음갱신이 1.5e9~2.2e9초 범위, 메시지를 끝까지 정확히 소비해야 함.
- **점수 = 직전 랭킹 갱신 순간의 총 포인트**(실시간 아님). 근거(2026-10-12 아라): 01:13:54 갱신분 41,043,747 →
  그 시간 실측 획득 +5,900, +5,126 → 02:13:54 갱신분 41,054,773 (= 41,043,747 + 11,026, 01:47:51 실측 총점과 같음).
- **목록 범위**(02:44 녹화): 분류마다 **상위 500명**(1~500위)만 온다. 전체수: ALL 10,000, 직업별 1,215~3,411.
  500위 점수는 ALL 약 1,760만, 직업별 약 490만~700만. 직업 분류는 2~9, 12 확인. 목록은 서버 구분 없이 한 종족 전체.
- 직업 분류를 고르면 `57 8D`도 그 분류의 내 순위로 온다(아라: ALL 167위, 분류 8에서 23위).

### 3.4.1 `33 36` 입장 (내 캐릭터)

```
33 36  varint 내부번호  5바이트(미확인)  string 이름  u16 서버코드  …(수 KB 캐릭터 정보)
```

- 접속, 캐릭터 변경, 지역 이동, 부활 때마다 1번(부활은 같은 내부번호). 캐릭터 변경은 TCP 연결을 새로 맺지 않는다.
- 직후(0.2~2.5초) `57 8D`(분류 0)가 랭킹 창을 열지 않아도 온다. 그 점수는 랭킹 갱신 때 값(실시간 아님).
- **내 총 포인트가 들어 있다** (2026-10-12): `f4 cb 1f`로 끝나는 태그(`21 f4 cb 1f`, `24 f4 cb 1f`) 바로 뒤의 u64. 메시지 안에 그런 자리는 정확히 하나였고
  (보리 12건·아라 5건, 길이 3199~4117), 그 직전 `73 E2`의 총점과 같았으며 다음 `73 E2`는 거기서 +13, +15처럼 작게 올랐다.
  위치는 끝에서 보리 146~151바이트, 아라 952바이트로 달라서 태그로 찾는다. 앱: `EnterWorldMessage.Points`.
  (`PcapDump --enter-totals`, `--find-totals`로 확인. 다른 메시지에는 총점이 없었다: `57 8D`의 랭킹 점수만 다른 값.)
- 근거: 2026-10-12 01:37 녹화(아라→보리→아라), 01:45 녹화(지역 이동 2회). 5바이트는 5f a1|b1 eb|e1 3a|38 37.

### 3.6 `04 38` 피해 (일부 해독, 2026-10-12)
같은 이름의 메시지가 전투 중 계속 온다(녹화 하나에 1천~3천 개). **피해량이 들어 있는 것은 그중 일부**(34~44바이트)이고,
나머지(26~28바이트, 약 97%)는 양이 없는 다른 이벤트다(아직 해석 못 함).
```
04 38
varint 피해를 받은 쪽 번호 (target)
u8     플래그 (0x04 = 회복: target = source / 0x06, 0x16, 0x26, 0x36 = 피해. 나머지 의미 미확인)
u8     (미확인, 전부 0)
varint 준 쪽 번호 (source)
...    (target 현재 상태 등으로 보이는 값들, 미확인)
u32    1                      ← 이 4바이트(01 00 00 00)를 기준점으로 쓴다
varint 스킬 계열 번호 (내 피해는 전부 같은 값, 스킬별 구분은 아님 / 미확인)
varint 총합 = 본 피해 + 추가 대미지 합계
[ varint n, n × varint 추가 대미지 ]   (추가 대미지가 있을 때만; 총합 바로 뒤)
01 00
```
- **검증** (훈련용 허수아비 전투 녹화 vs 게임 채팅의 전투 기록, 아라 = 3218, 허수아비 = 38750):
  채팅 `29,917` → 총합 29,917 / `53,621` + `1,531`×4 → 총합 59,745 / `133,825` + `3,616`×2 → 141,057 /
  `248,784` + `6,910`×3 → 269,514 / `37,381` + `1,010`×2 → 39,401. 전부 일치.
  채팅은 본 피해와 추가 대미지를 따로 적고, 패킷은 합쳐서 보낸다 → `본 피해 = 총합 − 추가 합계`.
- 번호는 앞이 **받은 쪽**, 뒤가 **준 쪽**이다 (사망 `04 8D`와 같은 순서). 내 회복(채팅 "생명력을 회복")은 `3218→3218`, 허수아비의 자기 회복(스킬 10000)은 `38750→38750`으로 온다.
- 시야 안의 **다른 플레이어가 준 피해도 온다** (같은 허수아비를 친 #37861의 8회가 같이 녹화됨).
- 이 녹화의 요약(`dotnet run --project tools/PcapDump -- --damage <pcap>`): 나 → 허수아비 23회 총 2,252,417 (본 2,192,706 + 추가 59,711).
- **54분 녹화(몬스터 전투 포함, 04 38 약 40만 개) 확인**:
  - 해독되는 피해 메시지는 약 2만 개(5%). 첫 플래그가 `0x04`(회복, target = source)가 1만 7천, `0x06/0x16/0x26/0x36`(피해)가 약 3천, `0x24`(회복 + 추가값)가 34.
    `0x46/0x54/0x56`은 다른 구조인데 우연히 비슷하게 읽혀서(총합 뒤의 4바이트 값이 "추가 대미지"로 읽힘) **추가 합계가 총합보다 크면 피해가 아닌 것으로 거른다**.
  - 플래그 비트 추정: `0x02` = 피해(없으면 회복), `0x20` = 추가 대미지 있음. `0x10`은 채팅의 치명타 종류와 맞지 않아 의미 미확인.
  - "스킬 번호" 칸은 내 피해 전부 같은 값(허수아비 전투 18002, 몬스터 전투 20993): 스킬이 아니라 캐릭터·직업 계열 번호로 보인다.
  - 몬스터 전투(2분, 아라 → 몬스터 #27094): **652회, 총 69,659,844 (본 49,500,625 + 추가 20,159,219)**. 같은 몬스터를 친 다른 플레이어 몫도 같이 온다.
  - **받은 피해도 온다**: 내가 target인 이벤트가 있다 (다른 플레이어 → 나, 몬스터 → 나 3회 77). 존 이동 때 내 번호가 바뀐다(3218 → 6212): `33 36` 입장 메시지의 번호를 따라간다.
  - 받는 쪽 번호 뒤에서 반복되는 3바이트 값(X)은 같은 효과가 다시 올 때 같은 값(허수아비 전투의 "주신의 은총" 230609가 몬스터 전투에서도 81번 반복)이고, 바로 뒤 4바이트는 같은 X에서 같지만 X가 하나 늘면 조금 커진다

### 3.6.1 `04 38` 피해의 수식어 (치명타·강타·방향, 해독 중, 2026-10-12)

허수아비 녹화(20:01~20:02, 같은 3스킬을 여러 효과로)와 19:15·19:45 로그를 맞춘 결과. 피해 메시지에서 출처 번호 뒤 `…스탬프 앞` 5바이트가 `[번호][X][F][00][방향]`이다 (태그가 달린 타격):
- **방향**(끝 바이트): `02` 전방, `01` 후방, `00` 방향 태그 없음. 40여 건 모두 맞았다.
- **X**: `03` 치명타, `02` 치명타 아님. 26건 모두 맞았다 (같은 스킬·같은 F에서 치명타인 것과 아닌 것이 X만 달랐다).
- **F**: `0x08` 강타 (태그가 있는 25건 모두). `0x04`는 완벽으로 보이나 `0x08`과 같이 켜진 경우(`8c`, `0c`)에 로그에는 강타만 나온다 → 둘이 같이 있으면 강타만 표시하는 것으로 추정. `0x80`은 스킬마다 다르다.
- 막기 (방패/무기 막기)는 구조가 달라 아직 못 풀었다. 태그가 없는 일반 타격은 이 자리에 가변 길이 값이 와서 구조가 다르다 (`F`의 `0x20` 비트가 켜져 있음).
- **막기** (20:11 녹화, 사랑의 베기 계열 80여 건): `F`의 `0x01` 방패 막기, `0x02` 무기 막기, `0x40` 완벽 막기(`c1` 완벽 방패, `c2` 완벽 무기). 막기 타격은 방향이 항상 `02`(전방)이고 로그에 전방이 안 나온다 (막기는 전방일 때만 된다는 게 맞다).
- **흡혈 꼬리**: 흡혈 스킬의 타격은 `01 00` 뒤에 공격자가 회복한 양(varint)이 한 번 더 붙는다 (빠른 베기 713 → 405 회복 등 로그와 일치). 이 꼬리가 있는 메시지는 예전 파서가 통째로 버렸다 → 0.1.17부터 읽는다.
- **천벌은 두 키**: 한 번 쓸 때마다 `65a0` 타격과 0.1초 뒤 같은 대상에게 `6591` 타격이 온다 (옆의 소환수에게는 `6591`만). 로그는 둘 다 "천벌"로 적는다 → 한 스킬로 합쳐 센다 (`Skills.Canonical`). 횟수는 두 타격을 합친 값이다.
- **효과 꼬리(플래그 `0x40`)**: 내 효과(보호막 등)를 만난 타격은 추가 대미지 목록 뒤에 "개수 + 그 효과의 스탬프 u32"가 더 붙는다 (`01 afdeea69`, `01 77e3d467` = 유스티엘의 권능 `67d4`). 예전 파서는 이런 타격(플래그 `0x46`/`0x56`/`0x76`)을 통째로 버렸다 → 21:29 결투의 심장 찌르기 1,407(+234×4)·섬광 베기 2,768이 빠지던 것이 이것이다. 추가 대미지 목록은 플래그 `0x20`이 있을 때만 있다. (보호막이 막아 준 양은 이 메시지에서 못 찾았다.)
- **검증 (20:18 녹화, 인게임 "받은 피해" 통계표와 대조)**: 35타격 / 총 38,213 / 치명타 33 / 강타 15 / 전방 7 후방 28 / 다단히트 25 / 재생 17 / 막기 4 / 완벽 0 — 패킷에서 센 값이 **전부 같았다**.
  - 치명타 = 두 번째 바이트(`count`)가 `03`, 강타 = `F & 0x08`, 방향 = 스탬프 바로 앞 바이트(`02` 전방, `01` 후방), 막기 = `F & 0x03`(단 `F & 0xE0 == 0xA0`이면 값이 이어지는 형태라 제외), 재생 = `F & 0x20`, 다단히트 = 추가 대미지 목록이 있는 타격(`flags 0x30`).
  - **타격 번호**: 스킬 앞 u32(`01 00 00 00`)는 다단히트 스킬의 몇 번째 타격인지(1~4)다. 메시지 끝도 `번호 00`이다. 예전 파서는 1번째만 읽어서 2~4번째 타격이 통째로 빠졌다 (표의 합계가 63%만 나왔다) → 고침.
  - **회복 꼬리**: `번호 00` 뒤의 varint가 회복량이다 (20:11 로그의 "N의 생명력을 회복했습니다"와 405·424·425·427·430 모두 일치). 20:18의 재생 17타격에는 이 꼬리가 없었고, `F`의 `0x20` 뒤 값(예: `c4 01`)이 회복량인지는 확인하지 못했다 (인게임에 표시가 없다).
- 앱: 자세히 보기 창에 위 통계가 나온다 (`HitStats`, 처치 DB의 `dealt_how`/`received_how`). 확인 도구: `PcapDump --hits <pcap> <내 번호> HH:mm:ss HH:mm:ss`. `PcapDump --taken <pcap> HH:mm`이 `F`와 원시 바이트를 보여준다.
- **생명력 회복과 행동력·정신력 회복은 메시지로 구분되지 않는다 (2026-10-14).** 같은 `04 38`(대미지 플래그 없음)이고, 구조에 "무엇을 회복했는지" 필드가 없다. 단 **행동력은 화면 숫자의 100배**로 온다 (생명의 권능 "200의 행동력" = 20,000, 충격 해제 1000 = 100,000, 보호의 방패 = 26,000). 효과(스킬 키 + 스탬프 하위 16비트)마다 생명력인지 행동력인지가 정해져 있다: 생명의 권능은 `1f97` = 행동력, `237f`·`2703` = 생명력. 녹화 40개 검사: 행동력 효과는 **모든 메시지가 100의 배수** (생명의 권능 1f97 162/162, 충격 해제 10/10, 이름 모르는 `6c1f`/7448 25,000 29/29와 `6c4d`/47ed 100,000 16/16), 생명력 효과는 우연히 100의 배수인 것이 1% 안팎 (치유의 빛 4/198 등). 앱: 한 번이라도 100의 배수가 아닌 값이 온 효과는 생명력, 100의 배수로만 오는 효과는 행동력으로 보고 받은 회복에서 뺀다 (`DamageLedger.AddHeal`). 한계: 효과의 첫 메시지가 우연히 100의 배수인 생명력 회복은 한 번 빠진다.


### 3.10 `41 36` 등장 (소환수의 주인)

- 근처에 무언가 나타날 때 오는 메시지 (번호 varint 뒤 수십~수백 바이트). **소환수는 앞부분에 `01 <길이> <주인 이름>`이 있다**: `4136 fe8503 5f000000 01 06 ec9584eb9dbc` = 49918번, 주인 아라 (로그의 "신성한 기운 [아라]").
- 19:45 녹화: 아라이 주인인 등장 25건 중 신성한 기운(`6638`)으로 피해를 준 번호는 모두 그 목록에 있었다. 다른 성직자(니들이치유를알아, 얌비 등)의 신성한 기운은 각자 이름으로 나온다.
- **종류 값 (2026-10-13)**: 번호 뒤는 `5f` + 3바이트, 그다음 **`01 <길이> <주인 이름>`(플레이어의 소환수) 또는 `00` 하나(주인 이름이 없는 것)**, 그다음 **u32 하나가 그것의 종류**(NPC 번호)다: `cb 90 2c 00` = 신성한 기운, 정령은 `xx 8e 2c 00`.
  - 정령의 종류 값 (전투 분석기 표와 소스 번호별 합계가 정확히 맞아서 확인): `fe` 고대의 정령(`2c8efe`), `b3` 불의 정령, `d3` 바람의 정령, `ef` 땅의 정령, `c7` 물의 정령. 같은 종류의 정령 여러 마리는 같은 값을 가진다 (불 3마리 모두 `b3`).
  - **정령은 스킬 번호를 나눠 쓴다**: `0098`(정령 기본 공격), `5f5f`(고대 파괴 / 불 화염 폭발 / 바람 회오리), `5f60`(고대 자기 폭풍 / 불 운석 소환). 이름은 때린 정령의 종류로 나뉜다. 앱은 (종류 << 16 | 번호)로 따로 세고 (`Skills.SpiritKey`), 이름은 표에 있다 (`0x20098` = 불의 정령: 기본공격 ...).
  - **주인은 이름이 아니라 번호로 들어 있다**: 메시지 안쪽의 `07 02 06 <u32> 34 08`에서 u32가 주인 플레이어의 번호다 (보리가 허수아비를 친 17:04 녹화: 정령 등장 20건 모두 11939 = 허수아비에 37M을 준 플레이어 번호). 정령은 주인 이름 칸이 비어 있어서 이름으로는 알아볼 수 없다. 앱은 이름 또는 이 번호가 내 번호면 내 소환수로 기억한다 (`SpawnMessage.OwnerEntity`). 신성한 기운의 같은 위치 값도 주인 번호로 보이지만(아라 소환수 3건 7000·14481: 존마다 번호가 달라서 확인 정도) 이름으로 이미 알아본다.
  - 같은 메시지 뒤쪽의 `fb 03 06 <이름>`은 **주인의 레기온(길드) 이름**이다 (사용자 확인: 보리의 정령 20건 모두 "하나" = 보리의 레기온). 아라의 신성한 기운 등장에도 "아리"가 있어서 같은 레기온이다. 앱은 아직 이 값을 쓰지 않는다.
  - 분석 도구: `PcapDump --skills-table <pcap> <표.txt>`는 정령 종류로 나눈 이름으로 맞춘다.
- 앱: 주인이 내 이름이거나 주인 번호가 내 번호인 몬스터 번호(16384 이상)를 내 소환수로 기억하고, 그 피해를 내 준 피해로 센다. 연결이 바뀌거나 입장하면 잊는다.

### 3.12 회피 (2026-10-14)

- **회피 = 피해 메시지(`04 38`)에서 종류 바이트가 `02`(`04`가 없음)이고 피해량이 없는 것.** 맞은 피해(`06`)와 같은 모양에서 "스킬 번호 varint 다음의 피해량"만 빠져서 29~30바이트다 (맞은 것은 31바이트 이상). 끝은 `<타격 번호> 00`.
- 예 (02:19:56.971): `0438 b93c 02 00 d98d01 f4c810 00 03 01 20 00 02 5b7f8e06 01000000 904e 01 00` (대상 = 나, 공격자 = 크로카).
- 검증: 채팅 로그 "저격하는 크로카의 공격을 회피했습니다" 02:19, 02:20이 02:19:56.971, 02:20:58.569의 이 메시지와 로그 순서까지 맞는다 (앞뒤로 맞은 피해 1, 바람의 활력 효과 / 경계의 눈 1,120 회복). 그 녹화에 나에게 온 회피가 49건 (몹 3마리).
- **내 공격을 상대가 회피한 쪽도 같은 모양이다 (공격자 = 나, 대상 = 상대).** 02:46:30.968 `0438 8a13 02 00 b331 62efd500 02 01 10 00 02 2be29053 01000000 e48901 01 00` (살두부가 저격을 회피). 02:46 한 분 동안 이 모양이 16건이고 채팅 로그의 "살두부가 ... 회피했습니다"도 16줄로 같다 (저격 1, 조준 화살 1, 올가미 1, 연사 3, 족쇄 1, 속사 3+1+3, 나선 1, 질풍 1). 다단 스킬은 타격마다 한 건씩 (타격 번호 1, 2, 3).
- 모르는 것: 종류 `02`만 있는 다른 "맞지 않음"(무적 등)이 섞일 가능성은 배제하지 못했다.
- 앱: `DodgeMessage` → 사람이 나를 공격해 맞지 않은 것은 받은 피해 쪽, 내 공격을 사람이 회피한 것은 준 피해 쪽 `HitStats.Dodge`에 센다 (몹은 상세 정보가 없으므로 세지 않음). 표시: 두 합계 줄의 "회피 N%" = 회피 ÷ (맞은 횟수 + 회피). 저장: `HitStats` 15번째 필드 (있을 때만).
### 3.9 회복 (2026-10-12)

전투 로그의 문장은 서버가 보내지 않는다 ("회복", "대미지", "재생의 빛" 글자가 패킷에 없음): 클라이언트가 숫자 이벤트로 만든다.
- 즉시 회복: `04 38`에서 첫 플래그에 `0x02`(피해)가 없는 것(`0x04`). 받는 사람(target)이 회복한 사람. 금액은 로그와 같다 (쾌유의 광휘 `660b` 9,752 / 14,041, 치유의 빛 `65ec` 4,356 / 5,612, 생명의 권능 `6648` 2,400 등; 21:04 녹화).
- **행동력 회복**: 생명의 권능은 "200의 행동력"을 같이 회복하는데 `6648` 금액 **20000**으로 온다 (생명력과 구분하는 필드는 못 찾음) → 앱은 `6648`의 20000을 뺀다.
- **지속 회복(재생의 빛)**: `05 38` 중 세 번째 바이트가 `0B`인 것 = 효과 한 번의 틱: `[대상][0B][출처][47][u32 스탬프(상위 16비트=스킬 `65dd`)][카운터][금액][값][01]`. 2초마다 1,203 (로그와 같음). `09`형(금액 없음)은 효과 발생 알림. 다른 `05 38`은 상태 갱신이라 읽지 않는다.
- **재생 스탯** ("재생이 터지면 받는 피해의 20%를 회복"): 피해 메시지에서 `F`의 `0x20` 비트가 켜진 타격이 재생이 터진 타격이고, 그 타격에 회복량이 **들어 있다**: `F` 바로 뒤 varint (`a0 c4 01 02`의 `c4 01` = 196). 값이 타격 합계(주 피해 + 추가 대미지)의 정확히 20%(내림)다: 984→196, 1,208→241, 1,646→329, 431→86, 23→4. 20:18 녹화 17번의 재생 합계 3,366이 "합계의 20%" 3,366과 같았다 (`PcapDump --hits`가 둘을 비교해 보여준다). 막은 타격(피해 1)은 0. 내가 맞은 타격의 재생은 내 회복, 내가 준 타격의 재생은 상대의 회복이다.
- 앱은 **내가 받은 회복**만 센다 (내가 쓴 것과 남이 준 것 모두; 남에게 준 회복은 안 센다). 싸움의 첫 타격부터 지금까지를 그 싸움(처치/사망)에 붙인다. 자세히 보기 창에 "받은 회복"으로 나온다.
- **지속 피해(2026-10-13)**: `05 38` 중 세 번째 바이트가 **`0A`**인 것 = 상대에게 걸린 디버프의 피해 틱 (파멸의 목소리, 약화의 낙인, 저주의 구름 ...): `[대상][0A][출처][varint][u32 스탬프(상위 16비트=스킬 키)][금액][48][varint][01]`. 0.5초마다 한 틱(금액은 조금씩 다름). 전투 분석기 표의 합계와 정확히 맞았다: 표에는 타격 수(HIT)에는 안 세지만 총 피해량에는 **표를 찍은 시각까지의 틱**이 더해진다. 파멸의 목소리 43틱 = 284,912, 약화의 낙인 24틱 = 86,217, 고통의 연쇄 7틱 = 31,930, 저주의 구름 19틱 = 109,976, 불의 장벽 4틱 = 18,293, 냉기 폭풍 5틱 = 15,920 (모두 표와 1 단위까지 같음). 앱은 이 틱을 플레이어와 나(또는 내 소환수) 사이의 피해로 센다: 총 피해와 스킬 합계에 더하고 타수에는 세지 않는다 (표도 타수에 세지 않는다). 디버프의 틱 키는 타격 키와 같거나 하나 낮다 (협공: 저주 틱 `6033` / 타격 `6034`, 협공: 부식 틱 `6042` / 타격 `6043`): `Skills`의 별칭으로 합친다. 도구: `PcapDump --periodic <pcap> <시각 접두어> [list]`, `--skills-table`이 표와 맞출 때 쓴다.
- **효과가 걸림 (`2a 38`, 2026-11-24, 마르쿠탄의 분노를 몬스터에게 쓴 녹화)**: `[대상][01][종류 11/13][핸들 varint][u32 효과 번호][u32 지속 ms][u32 0][u64 시각][시전자 varint]...`. 종류 `13`은 시간이 있는 효과(기절 3000, 받는 치유량 감소 10000, 물약 10000, 약화의 낙인 10000 ...), `11`은 스킬 자체의 상태와 패시브(지속 0 또는 4294967295 = 영구). **효과 번호 = 스킬 번호 × 10 + 순번** (183300301 = 마르쿠탄의 분노 18330030의 1번 효과; 기절 100000311처럼 스킬이 아닌 공통 효과도 있다). 한 번 쓰면 효과마다 한 건씩 온다: 기절 3000ms `100000311`, 치유량 감소 10000ms `183300301`, 5000ms `187800011`. 끝날 때는 3.0초, 5.1초, 10.0초 뒤에 `2c 38 [대상][01][00][핸들][01]`이 온다 (끝난 효과의 핸들; 핸들은 걸린 순서대로 1, 3, 2). 85,000건의 `2a 38` 중 플레이어에게 다른 플레이어가 건 효과가 약 16,000건 (기절 283, 약화의 낙인 475, 고통의 연쇄 275 ...). 허수아비는 CC 면역이라 기절/둔화 메시지가 오지 않고, `05 38` 종류 `00` + `2d 38` (값 100000010)이 오는데 면역 알림으로 보인다. 분쇄격(2026-11-24 23:00): 몬스터에게 `181300002` (분쇄격 자신의 효과, 5000ms)와 `100001301` (허점으로 보는 공통 효과, 5000ms)가 오고, 호법의 공격마다 몬스터에게 `187800011` (대지의 약속으로 보는 효과, 5000ms)과 시전자에게 `187300011`이 같이 온다 (설명의 5초 PVE/PVP 피해 내성 감소와 지속 시간이 맞다; 이름은 추정). 앱의 **디버프 알림**은 이 메시지로 알아내고, 효과 번호가 가진 스킬 이름(없으면 직전에 같은 적에게 맞은 스킬 이름)으로 구별한다 (`DebuffWatcher`).
- **플래그에 `0x02`가 없는 타격**: 소환수가 허수아비(NPC)에 준 타격 중 플래그 `0x04`/`0x24`인 것(`04 38`, 대상 ≠ 출처, 추가 피해 포함)은 피해다 (혹한의 바람 104타 중 21타: 포함하면 표의 104타 / 4,627,428과 정확히 맞는다). 반대로 **플레이어가 대상이면 `0x02` 없는 타격은 회복이다** (치유의 빛, 광휘, 가호, 권능: 이전 녹화 4개에서 확인). 그래서 앱의 `DamageLedger`는 그대로 `0x02`가 없으면 회복으로 본다 (플레이어만 따라가므로 NPC 대상의 `0x04` 피해는 필요 없다). `PcapDump --skills-table`은 NPC 대상에서는 `0x04`도 피해로 센다.
- **받은 타격의 막기 종류 (2026-10-13, 수호성이 허수아비에게 맞음, 두 녹화 31대가 로그와 모두 일치)**: `F` 바이트(수정자 영역)와 로그 표기: `0x01` = [방패 막기], `0x02` = [무기 막기], `0x11`, `0x31`, `0x32` = [철벽] (막기 종류와 무관하게 `0x10`이 있으면), `0x41` = [완벽 방패 막기], `0x42` = [완벽 무기 막기] (2026-10-13 18:58:42, 그 녹화의 `0x42`는 이 한 대뿐), `0x21`과 `0x61` = **표기 없음**, `0x00`과 `0x20` = [전방]/[후방] 또는 표기 없음 (막기 비트가 없어서 회복도 따라오지 않는다; 방향 바이트 2/1). 낮은 두 비트가 막기 종류(1 방패, 2 무기), `0x10`이 철벽, `0x40`이 완벽, `0x20`은 재생이 같이 켜진 것이고 막기 표기를 가린다 (`0x21`, `0x61`도 막기다: 아래 비호의 방패가 따라온다). 앱은 막기, 철벽(`HitMods.Immune`), 완벽 막기(`HitMods.PerfectBlock`)를 **따로** 센다 (자세히 보기의 "막기 %", "철벽 %", "완벽 막기 %").
- **비호의 방패의 회복(`4bd1`, 640~830)은 막기마다 따라온다**: 막기 비트가 있는 타격 25대 모두 0.1초 뒤에 회복이 왔고, 막기 비트가 없는 `0x00`(전방/후방) 6대에는 없었다. 그러니 `F`의 낮은 비트가 막기라는 확인이 하나 더 된다 (표기 없음 `0x21`·`0x61` 포함).
- **성직자의 주신의 가호도 막기마다 회복한다 (아라, 18:57~18:59 10대 중 막기 비트가 있는 8대 모두 0.1초 뒤, 1,461~1,720; `F=00`과 `F=20`에는 없음)**: 로그의 [무기 막기], [완벽 방패 막기], [철벽], [완벽 무기 막기], [방패 막기]와 표기 없음(`0x21`, `0x61`)이 `F` 값과 모두 맞았다 (`0x42` = [완벽 무기 막기], `0x32` = [철벽]).
- **보호의 방패 (수호성 스킬, 인게임 설명: 잠시 동안 막기 피해 감소 +100%, 확정 막기, 막기 성공 시 3초 이동 속도 +20%와 정신력·행동력 260 1회 회복)**: 막기 효과다. 시전 뒤 첫 막기에서 260 회복(키 `482e`: 정신력 260, 행동력 26000 = 260)이 나온다 (시전 전의 막기에서는 없음).
- **고정 추가 피해 (플래그 `0C`, 2026-10-13)**: 흡인 `5fb9`(390), 강습 낙인 `6980`(390), 강습 공포 `638a`(390씩 두 번) 때 **타격과 같은 밀리초에 따로 오는 `04 38`**: `[대상][0C 00][출처]...[스탬프(키)][타격 번호 u32][...][금액 390][64 00 00 00][타격 번호 00]`. 본 타격에는 들어 있지 않고 전투 분석기의 총 피해량에는 들어간다 (표와 5건 모두 정확히 맞음). 흡인의 흡혈은 이것이 아니라 0.1초 뒤에 나에게 오는 회복(플래그 `04`, 출처=대상=나, 같은 키, 300)이다 (앱은 이미 회복으로 센다). 390이 왜 고정값인지는 모른다. 다른 스킬과 PvP에서의 모양은 확인하지 못해서, 앱은 **위 모양과 정확히 같은 것만** 읽고 (그 밖의 `0C`는 버린다) 지속 피해 틱처럼 총 피해와 스킬 합계에만 더한다 (타수에는 세지 않는다).

- **전투 분석기 표의 퍼센트 칸 ↔ 앱의 수식어 (2026-10-13, 궁성 표 21행 × 6칸 전부 일치)**: CRI = 치명타, PERF = 완벽, **DOUB = 강타**, FRNT = 전방, BACK = 후방, MULT = 다단. (BLOC = 막기, IMMU = 철벽으로 보이나 이 표는 모두 0%라 확인하지 못했다.) `PcapDump --skills-table`은 표 줄 끝에 이 6개 숫자를 적으면 앱의 값과 비교해 준다.

### 3.8 `94` 계열 결투 (2026-10-12)

근거: 아라이 사랑과 결투 4번(패, 승, 패, 승) 한 녹화. 결과가 4번 모두 맞았다.

| 메시지 | 뜻 | 해독한 부분 |
|---|---|---|
| `01 94` | 결투 신청/요청 | u16 0, 내 번호(varint), 시각 |
| `05 94` | 수락(으로 추정) | 내 번호(varint), 결투 번호 |
| `09 94` | 결투 상태: 시작(`02`)과 3초 뒤 개시(`03`) | 결투 번호 u32, 내 번호 u32, 상태 1바이트, 두 이름 |
| `0A 94` | 결과 | 내 번호 u32, `02`, **승자 번호 u32**, 승자 이름, 패자 이름 |
| `0B 94` | 결과 (0A보다 50ms 뒤) | 내 번호 u32, `02`, **승자 번호 u32, 패자 번호 u32**, 승자 이름, 패자 이름 (이름은 길이 접두) |

- 앱은 `0B 94`만 읽는다. 내가 승자면 처치 명단에, 패자면 사망 명단에 들어간다 (포인트 0, "결투" 표시). 결투 중 서로 준 피해는 그 기록에 붙는다.
- 결투 중에는 죽지 않는 것으로 보인다 (사망 메시지 `04 8D` 없음).

### 3.7 `92` 계열 파티 (일부 해독, 2026-10-12)

근거: 녹화 2건 - 2인 파티를 맺고 푸는 것 2번, 3인 파티(보리가 파티장, 사랑·다솜; 인원 3으로 표시됨). 파티장이 아닐 때와 파티장이 나갈 때는 아직 못 봤다.

| 메시지 | 뜻 (추정) | 해독한 부분 |
|---|---|---|
| `00 92` | 파티 결성: 첫 구성원 정보 | `0x24` + 36자 GUID, u32 캐릭터 ID, 00 00, u16 서버, 이름(길이 접두) |
| `07 92` `08 92` | 다른 구성원이 들어옴 (`07`: 이름, `08`: GUID, 캐릭터 ID, 서버 … 이름, 끝 8바이트 시각) | `0D 92`가 없이 `08 92`만 오는 경우가 있어(3인 녹화) `08`도 구성원 추가로 쓴다 |
| `0D 92` `0E 92` | 구성원 상세 정보 | `0D 92`: GUID, 캐릭터 ID, 서버, 이름 |
| `11 92` | 구성원 하나가 나감 | u32 캐릭터 ID, 00 00, u16 서버 (10바이트) |
| `13 92` | `11 92` 직후에 옴 (파티 해산 알림으로 추정) | 안 씀 |
| `1B 92` `1C 92` | 구성원 상태 갱신 (약 1초 간격) | 안 씀 |

- **새 연결(지역 이동 등)의 `00 92`는 파티 전원을 한 번에 담는다** (2인: GUID 항목 2개, 341바이트; 헤더의 `02 01 00 02 NN`에서 NN=항목 수로 보임). 이 경우 `0D 92`/`08 92`는 따라 오지 않는다. 앱은 메시지 안의 GUID 항목을 모두 읽는다.
- GUID는 파티가 아니라 구성원마다 다르다 (같은 파티의 `00 92`와 `0D 92`에서 서로 달랐다).
- 캐릭터 ID는 랭킹 메시지의 캐릭터 ID와 같은 값 (보리 113395).
- 앱의 규칙: `00 92`는 새 파티를 시작, `08 92`·`0D 92`는 구성원 추가, `11 92`는 구성원 제거; 나 자신이 나가거나 구성원이 1명이 되면 파티 없음. 연결이 끊기거나 캐릭터가 바뀌면 초기화.
- 아직 모르는 것: 3인 이상일 때 `00 92`가 누구를 담는지(나/파티장), 내가 파티장일 때와 아닐 때의 차이, 파티장이 나갈 때, 공격대(여러 파티) 메시지.

## 5. 구간 기록 전송 (앱 → 수집 서버)

게임 패킷이 아니라 **우리 앱이 수집 서버로 보내는 JSON**이다 (설정 > "구간 기록 보내기", 동의했을 때만). 서버: `tools/UploadServer/serve_upload.py`, 같은 8443 포트·같은 공개키 고정·같은 `X-Aion2-Key` 헤더 (docs/RELEASE.md "데이터 수집 서버").

**구간(window)** = 앱이 센 한 덩어리. 보통 게임의 랭킹 초기화 시각에서 다음 초기화 시각까지 한 시간(예: 매시 13분 54초)이고, 중간에 측정을 멈추거나 앱을 끄거나 캐릭터를 바꾸거나 초기화 시각을 새로 알게 되면 그때까지로 **짧게 끊긴다**. **그 안에서 랭킹 포인트가 한 번이라도 움직였으면 모두** 만들고(`MeterSession.FlushWindows`), **한 번도 안 움직였으면 만들지 않는다**(측정만 켜 두고 쉬는 사용자가 서버를 채우지 않도록). 표시 방식(정각/랭킹 초기화)과 상관없이 별도의 `BucketBook`이 만든다. 끝난 지 10초 뒤에 만든다 (마지막 처치·미매칭 획득이 들어가도록. 멈춤·종료·캐릭터 변경으로 끊긴 것은 바로).
- **`cp` = 완전한 구간**: 게임의 두 초기화 시각 사이 한 시간 전체를 처음부터 끝까지 측정한 구간. 이때만 `t0`/`t1`이 두 초기화 시각의 총 포인트와 같아서, 나중에 랭킹(게임의 순위표, 상위 500명)과 대조하는 데 쓸 수 있다. 그 밖의 구간은 본인이 보는 용도.
- **`al` = 정렬됨**: 시작이 게임의 초기화 시각에 맞다. 초기화 시각을 모르던 때(랭킹 창을 연 적 없음)의 구간은 정각에서 끊어서 `al` = 0.
- 시작·종료를 모두 담는다: `start`/`end`(구간의 한계), `f`/`l`(첫·마지막 변화를 본 시각), `t0`/`t1`(첫 변화 직전·마지막 변화 직후의 총 포인트).

```
POST /windows   {"v":1,"install":"<32자리 16진수>","app":"0.1.25","windows":[ 구간, ... ]}   (한 번에 48개까지, 본문 256 KB까지)
구간 = {
  "c":  {"n": 내 캐릭터 이름, "s": 게임 서버 코드, "r": 랭킹 ID 또는 null},   (r = 서버 코드<<48 | 캐릭터 번호, 3.4)
  "start": 시작 unix초, "end": 끝 unix초 (0 < end - start <= 3600), "off": 시작이 시 정각 뒤 몇 초인지(= start % 3600),
  "f": 첫 변화 시각, "l": 마지막 변화 시각 (start <= f <= l <= end; 없으면 start/end),
  "t0": 첫 변화 직전 총 포인트, "t1": 마지막 변화 직후 총 포인트, "gain": 얻은 합, "loss": 잃은 합 (양수), "ev": 포인트 변화 횟수,
  "al": 0|1 (정렬됨), "cp": 0|1 (완전한 구간; 없으면 1: 첫 스키마),
  "p": [[파티 인원, gain, loss, 횟수], ...],
  "k": [[unix초, 종류(0 처치 1 사망 2 몬스터 3 결투), 포인트(결투는 +1 승 / -1 패), 상대 서버 코드, 상대 종족], ...],
        (**상대 이름은 서버로 보내지 않는다.** 이 PC에 보관하는 사본(`ToJson()`)에는 여섯 번째 칸으로 이름이 있고(처치는 피해자, 사망은 처치자,
         결투는 상대, 몬스터는 ""), 보낼 때(`ToJson(withNames: false)`)는 빠진다. 옛 앱이 보낸 여섯 번째 칸은 서버가 받자마자 버린다.)
  "un": 처치와 연결하지 못한 획득의 합 }
응답 200 {"accepted":n,"duplicate":n,"refused":n}
POST /windows/of       {"n":"캐릭터 이름","s":서버 코드,"install":"..."}  → {"windows":[ 구간 + "flags", ... ]}   (그 캐릭터의 구간, 최신순, 최대 168개. 앱의 "내 기록")
POST /windows/forget   {"install":"..."}  → {"deleted":n}   (이 설치가 보낸 구간을 지움: 동의 철회)
POST /windows/mine     {"install":"..."}  → {"windows":[...]}   (이 설치가 보낸 구간; 0.1.25 앱이 이렇게 물어서 남겨 둠)
```
- **캐릭터가 열쇠다**: 서버는 구간을 (캐릭터 이름, 서버 코드)로 묶고 그걸로 내준다 — 게임이 알려 주는 값이고 누구나 알 수 있으므로, **이름과 서버만으로는 읽기를 허용하지 않는다**: `/windows/of`는 설치 식별자를 함께 받고, **그 설치가 보낸 구간만** 내준다. 아니면 없는 캐릭터와 같은 빈 목록을 돌려준다 (물어봐서 알 수 있는 것이 없다). "그 캐릭터를 보낸 적이 있는 설치"로 넓히면 안 된다: 서버는 보낸 사람이 그 캐릭터의 주인인지 확인할 수 없어서, 남의 이름으로 가짜 구간 하나를 보내 읽기 권한을 얻을 수 있다. 서버의 기록은 캐릭터마다 하나이고 먼저 받은 것이 남으므로, 같은 캐릭터를 다른 PC가 보내면 그 PC는 먼저 받힌 구간을 서버에서 읽지 못한다(각 PC의 로컬 사본으로 본다). 서버에는 다른 사람의 이름도 올라오지 않는다. 앱을 다시 설치하면 새 설치 식별자가 생겨서 이전 설치가 보낸 기록은 읽을 수 없다 (설정 폴더를 지우지 않으면 식별자는 그대로다).
- 서버가 "이 앱이 정말 그 캐릭터의 것인가"를 확인할 방법은 없다 (접속 정보는 앱이 말해 주는 값). 가짜 기록은 랭킹 때 게임의 공식 순위표(상위 500명)와 교차 확인해서 거른다.
- `install`은 동의할 때 만드는 무작위 ID (`AppSettings.InstallId`). **읽는 열쇠가 아니라** 보낸 사람 표시일 뿐이고, 삭제할 때(그 설치가 보낸 것만)와 보낸 설치를 가리는 데 쓴다. 같은 (캐릭터, start, end)는 어느 설치가 보냈든 한 번만 저장된다 (먼저 받은 것이 남고, 중복 → `duplicate`). 같은 시간에 시작하고 끝이 다른 구간(멈췄다 다시 켠 경우)은 서로 다른 구간이다.
- **상대 이름은 이 PC에서만, 기본은 계속(`AppSettings.NameKeepDays` 0; 7·30이면 그 일수 뒤 삭제, 계속이어도 처치 `MeterStore.MaxKeptKills` 초과분은 오래된 것부터)**: "내 기록"은 서버의 숫자 기록에 이 PC의 처치 기록(`kills` 표)에서 같은 시각·종류·포인트인 것의 이름을 붙인다. 정한 일수가 지난 처치 기록과 구간 사본은 앱이 시작할 때와 매시간 지운다 (`PruneNames`). 기록 폴더의 CSV는 사용자의 파일이라 지우지 않는다.
- **받아들이는 조건**(어기면 `refused`, 표본을 `rejected` 표에 남김): 모양이 맞고, 한 시간 이내이고, `start % 3600 == off`, `start <= f <= l <= end`. 짧은 구간(`cp` = 0)도 받는다.
- **표시만 하고 저장하는 것**(`flags`, 한도를 정하기 전에 실제 값을 보려는 것): `gain-high` (한 시간에 100만 초과), `future`, `idle` (변화 0인 구간: 앱은 보내지 않음), `claim` (`cp` = 1이라면서 정렬된 한 시간이 아님). **`cp` = 1인 구간에만**: `net` (t1-t0 이 gain-loss 와 다름), `offset` (최근 500건의 완전한 구간에서 가장 흔한 시각과 2초 넘게 다름), `gap-before`/`gap-after` (이웃한 완전한 구간의 끝/시작 총합이 이어지지 않음). 짧은 구간은 사이에 못 본 변화가 있을 수 있어서 합계를 따지지 않는다.
- 보관: 캐릭터마다 최신 168구간(7일), 30일 동안 아무도 보내지 않은 캐릭터의 구간은 삭제, 표 전체 50만 줄 상한. IP 주소는 저장하지 않는다.
- 앱 쪽 대기열: `MeterStore`의 `window_records` 표 (`sent` = 서버로 보낼 것이 남았나, `exported` = 기록 파일에 쓸 것이 남았나; 둘 다 끝난 것은 14일 보관). 동의도 없고 기록 폴더도 없으면 만들어진 구간을 보관하지 않는다. 앱을 끌 때 진행 중이던 구간도 기록이 된다(`MeterSession.Shutdown`). 같은 구간이 기록 폴더의 CSV 두 개로도 나간다(docs/BEHAVIOR.md §1.7).
- 조회: `tools\windows-report.ps1` (서버에서 `windows_report.py`, 읽기 전용).
- 계획: 이 값들로 현실적인 한도를 정하고, 게임의 랭킹 목록(`55 8D`, 상위 500명의 이름·점수)을 여러 사용자가 올려 총 포인트를 교차 확인한다 (상위 500명에 한해).

### 3.12 내 조준 대상 `34 38` / `35 38` (2026-11-23, 양방향 녹화)
- 클릭하면 클라이언트가 6바이트(암호화)를 서버로 보내고, **20~50 ms 뒤 서버가 `34 38` + 00 00 00 + 개체 번호**를 보낸다 (플레이어는 u16: 7바이트, 몬스터는 3바이트: 8바이트). 이게 "내가 방금 고른 대상"이다.
- `35 38` + u32 (6바이트)는 그 직후 뒤따르고, 싸우는 동안 0.5~1.3초마다 되풀이되며, 게임이 대신 조준했을 때는 `34 38` 없이 혼자 온다. 더 긴 `35 38`(7~9바이트, 끝에 `E167` 등)은 쓰지 않는다.
- 조준 해제는 `34 38` + 영 4바이트 (6바이트). 해제와 같은 순간에 방금 대상의 `35 38`이 한 번 더 오기도 한다.
- 개체 번호는 신원 메시지(`45 36`)의 **메시지 맨 앞 2바이트(u16)**와 같다 (신원의 varint 번호와 다름). 신원 메시지에는 그 캐릭터의 직업 스킬 번호(`11790000`+1 꼴: 앞 두 자리가 직업, 11 검성·12 수호성·13 살성·14 궁성·15 마도성·16 정령성·17 치유성·18 호법성·19 권성)가 들어 있어 직업을 알 수 있다 (267명 중 267명 일치).
- 앱: `TargetWatcher`가 패킷 스레드에서 바로 처리한다 (`34 38`은 항상, `35 38`은 새 개체일 때만).
